PART 1: CORE WORKFLOW, LOGIN & DATA FLOW

Q1. What is Guardian Eye AI and how does the end-to-end workflow operate?

Answer: Guardian Eye AI is an enterprise multimodal video meeting and communication auditing platform. It allows users to run live meetings or upload pre-recorded videos to get an instant, objective evaluation of how each person communicates.

The end-to-end workflow has five clear steps: First, the user selects their role as Host or Participant. Second, the Host logs in while Participants enter a 6-character room code. Third, participants meet in a real-time WebRTC room (supporting up to 5 members) or upload a meeting video. Fourth, FFmpeg extracts clean 16kHz audio, Groq Whisper transcribes verbatim dialogue, and acoustic clustering detects who spoke what. Fifth, Google Gemini Flash grades each speaker out of 10 on communication metrics, audits question-and-answer exchanges for accuracy, and renders an interactive dashboard with instant PDF export.

Q2. What is the complete Data Flow across the system?

Answer: Data flows cleanly across four connected layers:

1. Client Layer (Port 5173): The React 19 frontend captures webcam video, microphone audio, and user actions. It handles live volume metering and file uploads.

2. Signaling Layer (Port 9000): The Node.js PeerJS server routes knock requests, room joins, and WebRTC handshakes between browsers so media streams connect directly peer-to-peer.

3. Core Backend Layer (Port 8000): The FastAPI Python backend handles user login, runs FFmpeg audio extraction, coordinates Groq Whisper transcription, and runs Gemini AI scoring.

4. Persistence Layer: SQLite (guardianeye.db) stores user accounts and room states. Browser IndexedDB stores recorded video files, and localStorage caches offline reports.

Q3. How does User Login work, how is the Gmail ID and password verified, and where is the password stored?

Answer: When a user logs in, the frontend checks that the email ends with @gmail.com (automatically appending it if missing) and ensures the password has at least 6 characters.

The password is verified using the industry-standard Bcrypt hashing algorithm with 12 salt rounds (4,096 computation cycles). The system never stores plaintext passwords. When a user registers, Bcrypt generates a secure one-way salted hash. On login, Bcrypt verifies the submitted password against the stored hash in the users table of SQLite database guardianeye.db. If verified, the server issues a session token. When cloud mode is enabled, it also authenticates via Google Firebase Auth.

PART 2: LIVE MEETING ROOM, WEBRTC CONNECTIVITY & ALGORITHMS

Q4. How does clicking "Create New" work and how does it open the camera?

Answer: Clicking "Create New" triggers the meeting setup modal, sends a creation request to POST /api/meetings/create to register the room code, and mounts the live MeetingRoom.jsx component.

The camera is accessed via a 4-stage progressive hardware fallback: Stage 1 asks for 720p HD video at 30 fps with echo cancellation, noise suppression, and auto gain control. If the camera rejects HD, Stage 2 requests basic video and audio. If the microphone is in use by another app, Stage 3 requests video only. If no camera exists, Stage 4 requests audio only. The stream is attached directly to the local video element on screen.

Q5. How does the Unique Room Code generation algorithm work?

Answer: Room codes use an unambiguous 6-character Base-32 alphanumeric sampling algorithm formatted as XXX-XXX (such as W4K-9P2).

The algorithm picks randomly from the character set ABCDEFGHJKLMNPQRSTUVWXYZ23456789. Confusing characters like 0, O, 1, and I are completely excluded so users never misread codes. Clicking the code badge in the meeting copies a direct link (http://localhost:5173/?join=W4K-9P2). When a guest opens this link, the app automatically pre-fills the room code on their screen.

Q6. How does the Join Request ("Knock" Notification) work when a Participant asks to join?

Answer: When a participant enters a room code, their browser calls the backend to find the Host's active peer connection. It then opens a reliable WebRTC data channel and sends a knock packet with the participant's name.

While the participant sees a waiting screen, a floating notification pops up on the Host's screen with the guest's name and Accept / Reject buttons. When the Host clicks Accept, the system verifies that the room has fewer than 5 members, approves the join request, notifies all existing peers, and initiates peer-to-peer audio/video calls.

Q7. What algorithms are used to connect multiple users' video and audio smoothly over the internet?

Answer: Four optimization algorithms work together to keep video calls smooth without lag:

1. Full-Mesh P2P with 8 STUN Servers: Connects browsers directly using Google and Cloudflare STUN servers to bypass residential firewalls and home routers.

2. SDP Codec Prioritization: Modifies the WebRTC session handshake text to prioritize hardware-accelerated H.264 and VP8 codecs, keeping CPU usage low.

3. Bandwidth Bitrate Capping: Caps video at 500 kbps (24 fps) while giving audio high priority, ensuring voices never stutter even on slow internet.

4. Adaptive Congestion Control: Monitors frame drops every 3.5 seconds. If packet loss exceeds 25%, it downscales video to 250 kbps; when stable, it restores full quality automatically.

Q8. How does the Microphone button, Default Mute, and Live Active-Speaker Detection work?

Answer: Every participant enters the room muted by default (audioOn = false) to avoid sudden feedback or background noise. Users must click the Mic button to unmute.

Clicking the Mic toggles the audio track and sends an update packet across data channels so everyone sees the live mic status. For active speaker detection, the Web Audio API connects a Fast Fourier Transform (FFT) analyser to each audio stream. Every 100 milliseconds, it measures sound volume across 128 frequencies. The person speaking with the highest energy above the noise floor is highlighted on screen with an active speaker badge.

Q9. How does the Record Button work in the live meeting room?

Answer: Clicking Record triggers the browser screen-sharing dialog to capture the video grid. Because standard browser recording only captures one audio track, Guardian Eye AI uses a custom Web Audio API multi-source audio mixer.

The mixer blends the host's microphone, all remote participants' incoming voices, and system tab sounds into one high-quality audio stream. A MediaRecorder encodes video and mixed audio into a WebM/MP4 file. When recording stops, the file is saved to IndexedDB, downloaded to the user's computer, and sent to the AI pipeline for instant transcription and scoring.

PART 3: STORAGE, VIDEO UPLOAD, API KEYS & AI PIPELINE ALGORITHMS

Q10. How does the History section work and where does the app store all its data?

Answer: The app uses a layered storage architecture for maximum speed and offline support:

Recorded video files are stored in browser IndexedDB (GuardianEyeRecordingsDB), allowing instant playback and deletion without consuming cloud bandwidth. Meeting summaries, scores, and transcripts are stored in SQLite on the backend and cached in browser localStorage. When cloud synchronization is active, records also sync to Google Cloud Firestore.

Q11. How does "Upload Recorded Meeting" extract audio and detect "Who Spoke What" (Speaker Diarization)?

Answer: When a user uploads any video, a four-stage acoustic and AI pipeline processes the file:

Stage 1 (FFmpeg Audio Extraction): Strips video frames and extracts clean 16,000 Hz, 16-bit mono WAV audio. For lightweight base64 delivery, it also creates a compact 48kbps MP3 under 15 MB.

Stage 2 (Voice Activity Detection - VAD): Analyzes root-mean-square energy across 50ms windows with an adaptive noise floor to isolate true speech segments from silence and background hum.

Stage 3 (6D Acoustic Voiceprint Clustering): Calculates 6 mathematical features for each speech segment: Pitch frequency (F0), Spectral Centroid (brightness), Bandwidth, Rolloff, Zero-Crossing Rate, and Energy. Segments are clustered by voice distance into distinct speakers.

Stage 4 (Google Gemini 2.5 Flash Native Audio Diarization): Gemini 2.5 Flash listens directly to the audio waveform, transcribes every turn verbatim with filler words, and maps each unique vocal pitch and turn-taking exchange directly to the user-entered participant names.

Q12. How do the Dual Gemini API Keys work, how did we get them, and how are they aligned in the backend?

Answer: The system uses two dedicated Google Gemini API keys stored safely in backend/.env for intelligent load splitting:

GEMINI_API_KEY_PRIMARY: Dedicated to heavy multimodal audio ingestion, diarization, and verbatim speech-to-text.

GEMINI_API_KEY_SECONDARY: Dedicated to cognitive 1–10 metric scoring, executive summarization, and Q&A fact-checking audits.

Both keys are obtained from Google AI Studio (aistudio.google.com) and are kept strictly on the server. If either key reaches Google API rate limits or quota, automatic failover instantly routes requests to the alternate key.

PART 4: SCORING ENGINE, RUBRICS & FACT-CHECKING

Q13. How does the Scoring Engine work and on what basis does it give marks out of 10?

Answer: The scoring engine combines hard mathematical speech measurements with Gemini AI auditing so grades are genuine and unbiased without default high scores:

First, the system calculates exact speech telemetry: Words Per Minute (optimal: 115–155 WPM), filler word count (such as "um", "uh", "like"), and hesitation pauses between 1.8 and 8 seconds.

Next, Gemini grades each speaker across 6 core numerical parameters on a strict 1 to 10 scale plus pragmatic delivery style: Communication Skills (clarity and structure), Fluency (smooth delivery and pacing), Confidence (decisive phrasing vs. tentative hedging), Awkwardness (inverted: 1/10 is smooth, higher numbers penalize heavy fillers and long pauses), Straightforward Answers (directness without dodging questions), Persuasive Assertiveness (1–10, measuring conviction, authoritative posture, and rhetorical impact), and Tone Style & Delivery Vector (identifies the speaker's pragmatic stance: Commanding, Requesting, Polite, or Collaborative).

Anti-hallucination guardrails enforce accuracy: If a person speaks fewer than 4 words (20 characters), their score is clamped to 1.0/10 with an "Insufficient text" notice. High filler rates (>6%) or multiple pauses automatically cap fluency and increase awkwardness.

Executive Score = 0.25*(Skills) + 0.25*(Fluency) + 0.20*(Confidence) + 0.20*(Straightforward) + 0.10*(11 - Awkwardness)
Q14. How does the Fact-Checking & Q&A Audit engine work?

Answer: The engine inspects every conversation turn to identify questions and pairs them with the responder's answer.

Questions are detected via question marks or interrogative starters (What, How, Why, When, Where, Who, Can, Could). The system pairs the question with the response and classifies the answer into one of three strict verdicts: Accurate (green badge, directly and factually answers the question), Incomplete (amber badge, vague, missing details, or relies on heavy fillers), or Evasive (red badge, deflects the question or uses evasive phrasing like "not sure" or "hard to say").

PART 5: ADVANCED CODEBASE CAPABILITIES & SECURITY

Q15. How do "Pin User", "Raise Hand", "Kick Participant", and "Meeting Notes" work?

Answer: These features provide full interactive control inside the live room:

Pin User: Highlights a chosen video tile with a cyan glowing border and locks the active speaker indicator onto that person. Raise Hand: Displays an animated hand icon on the user's video tile and broadcasts the state to all peers. Host Kick: Allows the host to remove a participant; confirming sends a kick message over the data channel and closes their video connection. Meeting Notes: Opens a notepad that automatically saves every typed character to browser localStorage so notes are never lost.

Q16. What is the 7-Dimension Communication Coach in the backend?

Answer: In addition to the meeting scorecard, the backend includes an executive coaching engine (/api/ai/coach) that evaluates speech on a 0 to 100 scale across 7 dimensions: Verbal Clarity (20%), Speaking Fluency (15%), Vocabulary Expression (15%), Presentation Structure (15%), Active Listening (15%), Professionalism (10%), and Conciseness (10%). It cites exact quotes and generates a step-by-step improvement practice plan.

Q17. How does the local Apple Silicon GPU (MPS) and PyAnnote pipeline work?

Answer: On macOS machines with Apple Silicon (M1/M2/M3), the backend automatically enables Apple Metal Performance Shaders (torch.device('mps')) for hardware acceleration. It can run local PyAnnote diarization and local Whisper transcription directly on the Mac's neural engine without sending audio to external clouds.

Q18. What happens if the backend server or internet is completely offline during audio analysis?

Answer: The app includes a 100% browser-native Web Audio API fallback engine (audioAnalyzer.js). If the backend is unreachable, the browser decodes the audio file directly into memory, computes speech energy windows, runs client-side voice activity detection, and displays speaker communication metrics without crashing.

Q19. How does the Multi-Page PDF Report Export work?

Answer: Clicking "Download PDF Report" uses html2canvas to capture the report dashboard at high Retina resolution (scale: 2) while hiding action buttons. It then uses jsPDF to cleanly slice the document into standard A4 pages. On mobile devices, it integrates with the native Web Share API so users can send the PDF via WhatsApp, email, or AirDrop with one tap.

Q20. How is the app packaged for Mobile Devices (Android APK & iOS PWA)?

Answer: For Android, the project is configured using Capacitor (com.guardianeye.ai) with camera and microphone permissions declared in AndroidManifest.xml, building directly into an Android APK. For iOS and desktop, it functions as a Progressive Web App (PWA) with an "Add to Home Screen" prompt for full-screen offline use.

Q21. How are cloud databases and file storage secured against unauthorized access?

Answer: Security is enforced at both cloud and server levels: Cloud Firestore and Firebase Storage security rules enforce strict document ownership so users can only read and write their own recordings and transcripts. On the backend, directory path traversal protection checks every file path with os.path.abspath, preventing unauthorized ../../ access with HTTP 403 Forbidden.

Q22. How is the project tested and verified?

Answer: The project includes four automated verification suites: test_production_suite.py tests authentication, video extraction, and room limits; crosscheck_all.py verifies multi-speaker clustering; simulation_test_suite.mjs audits WebRTC network traversal and SDP constraints; and test_e2e_pipeline.py verifies the full transcription and scoring pipeline.

Q23. How does the platform scale and maintain low latency during peak usage?

Answer: Peer-to-peer WebRTC mesh topology means video and audio streams flow directly between users rather than through an expensive media server. Audio extraction uses FFmpeg streaming pipes, and Groq Whisper transcribes 30-minute meetings in less than 5 seconds. Because compute runs on edge devices and high-speed Groq LPU chips, server hosting costs remain minimal.

Q24. How does Guardian Eye AI handle user privacy and zero data retention?

Answer: User privacy is built-in by design. Video recordings stay in the user's browser IndexedDB unless the user explicitly uploads them. Audio files processed by the backend are stored in temporary system directories that clean up automatically. Passwords are cryptographically hashed, and no private video streams are logged or stored on external servers.

Answer: Traditional video meeting apps (like Zoom or Google Meet) only transmit video and audio without understanding conversation quality. Guardian Eye AI bridges communication and intelligence: it provides smooth video conferencing and acts as an AI auditor that tracks speaking speed, eliminates filler words, holds speakers accountable with question-and-answer fact-checking, and generates executive-ready performance reports.
